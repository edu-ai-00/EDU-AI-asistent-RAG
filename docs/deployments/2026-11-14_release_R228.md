# Deployment: release R228 (QA search 217–225, knowledge-base portal 226–228, D11 takeover)

> **Rehearsed 14 Nov 2026 on lab VM 507, not deployed to production.** The lab ran production's
> commit 07ecaa2 as a clean install, loaded a fresh data-only copy of the production database
> (31 tables, row counts identical), and was then updated to this branch exactly as below.

## What production gets

- Curated QA search: negation, Czech without diacritics, typo repair, synonyms
  (`eduai_normalize` 3.4.1, migrations 217–225; details in
  [2026-10-21_normalize_3_3.md](2026-10-21_normalize_3_3.md)).
- The knowledge-base portal at `/knowledge/` (documents, QA, try a question; migrations
  226–228). The old address `/qa/` answers `404`.
- **No manual migrations.** Bootstrap step 4b takes the production database over
  (`migrate.py adopt`, D11: its schema must be exactly B216) and applies R228 after a local
  dump ([spec](../../specs/active/spec.migration-registry.md),
  [OPERATIONS_LINUX.md](../OPERATIONS_LINUX.md), "Database migrations from 217 on").
- A re-ingest of all QA packs and web documents, because 3.1–3.3 changed the stored forms.

## Steps (evening window; chat is briefly unavailable during step 4)

| # | What | Check |
|---|---|---|
| 1 | AWS snapshot of the volume (rollback point); wait until `completed` | snapshot id noted |
| 2 | `cd ~/edu-ai/src && git status --short && git pull` | clean tree, new HEAD |
| 3 | `python3 scripts/migrate.py adopt --check --container edu_ai_postgres` (read-only) | `adopt check ok: the schema is exactly B216` — otherwise **stop** |
| 4 | `python3 scripts/setup.py install` | step 4b: `taking it over`, `adopt ok`, 12× `applying`, `database at release R228`; smoke without FAIL; `database roles MATCH` |
| 5 | `docker exec edu_ai_nginx nginx -t && docker exec edu_ai_nginx nginx -s reload` | `/knowledge/` 200, `/qa/` 404 on port 80; both 404 on 81 |
| 6 | Re-ingest: `docker cp scripts/reingest_content.py edu_ai_qa_admin:/tmp/` then `docker exec edu_ai_qa_admin python /tmp/reingest_content.py --dry-run`, then without `--dry-run` | 9 QA packs `OK`; 23 web documents queued, all `completed` |
| 7 | Parity check (command in [AGENTS.md](../../AGENTS.md)); one question without an LLM ("Jak se jmenuje naše škola?"), one with | parity passes; answers |
| 8 | `python3 scripts/migrate.py status --container edu_ai_postgres --release R228` | `pending: 0`, `schema fingerprint: matches` |
| 9 | Delete the pre-apply dump: `rm ~/edu-ai/state/db_migration_dumps/*.dump` (it holds personal data) | directory empty |

Expected durations on the lab: step 4 about 5 minutes (the takeover and the 12 migrations
together about 30 seconds); step 6 a few minutes for QA, about 20 minutes for the web pages
(one page at a time through the gateway).

**Return.** Before step 6: restore the snapshot (`aws ec2 create-replace-root-volume-task`),
or keep the database and go back to the previous images; the migrations change settings
(each has an undo line in the 2026-10-21 note) and add one column and grants, which the old
code ignores. After step 6 the snapshot is the way back; logged questions after it are lost.

Asked in retrieval-only mode (no LLM), 15 of them also with generation; compared with the

QA variant keeps a negated word under its positive lemma (`nesmí` → `nesmet`).

## Known effects

- The new versions of re-ingested packs and pages carry the school's technical portal
  account as uploader; content, visibility and roles are unchanged.
- While the gateway ingests a page, the portal's job list can take tens of seconds to
  answer (it asks the busy gateway for chunk counts).
- The portal records the content hash of a refreshed page on a later job listing; a few
  pages may show none until then.
