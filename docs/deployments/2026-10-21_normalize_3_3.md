# Deployment: eduai_normalize 3.3.0 (negation, stop-words, diacritics), synonym groups 217

> **Prepared 21 Oct 2026, extended until 10 Nov 2026; not deployed to production.** Verified on the
> lab installation (no QA packs, no documents in its database), where 217–223 are applied.

## Summary for the operator

Recommended configuration for operation without a key: normalization 3.3.0 and migrations
**217–223**, `rank_ties` left off (see below). Each migration is a settings or data change with
its own self-check and an undo line in its section here.

| Step | What | Check |
|---|---|---|
| 1 | Rebuild **both** images (`edu_ai_search`, `edu_ai`) from this branch | both report `eduai_normalize` 3.3.0; the search image contains `qa_ngram.py` |
| 2 | Back up `settings` and `qa_stopword` | — |
| 3 | Apply 217 → 223 in order, one transaction per file | every file ends without `RAISE EXCEPTION` |
| 4 | Re-ingest every QA pack and every document | stored lemmas come from 3.3.0 |
| 5 | Parity check (`contracts/parity/check_vectors.py`, command in [AGENTS.md](../../AGENTS.md)) | passes |
| 6 | One question without a key | an answer, an offer or `no_answer`, never `llm_unavailable` |

The settings take effect within the settings cache TTL (5 s); only the code needs the rebuild.
On the lab installation the steps were done by hand with `psql -1` per file; `migrate.py` is
approved for isolated databases only (D11, taking over an existing installation, is open).

## What changes

- `eduai_normalize` **3.1.0**: a Czech lemma keeps its negation. simplemma 2.0.0
  reduced "nesmím" and "smím" to the same `smět`; now `nesmět`. Rule in
  [`lemmatizer.py`](../../search/eduai_normalize/eduai_normalize/lemmatizer.py),
  cases in the [parity vectors](../../contracts/parity/cs-normalization-vectors.json).
- `eduai_normalize` **3.2.0**: the lemma and stem branches judge a stop-word
  by its SURFACE form before reducing. 44 of the 155 Czech index stop-words
  used to leak (jsou → stem `jso`, budou → `bud`, mezi → `meh`; 18 % of the
  JPZ phrasings), some colliding with content words ("během" → `beh` as
  "běh", "této" → lemma `teta`). English profits too ("does" → `doe`).
  Not migration 211's reduced-form columns: matching the stem `beh` would drop
  "běh" as well. The QA measurement moved no outcome (coverage reads lemmas,
  exact matches pass on the norm form); the gain is for document retrieval,
  which the lab could not measure without documents.
- `eduai_normalize` **3.3.0**: a Czech word typed WITHOUT diacritics that the
  dictionary does not know as typed is lemmatized through its spellings with
  diacritics, when they all agree on the lemma ("zacina" → začínat; "muze"
  stays, muže/může disagree; "rada" stays, it is a word). The spellings are
  generated and looked up in simplemma's dictionary — no reverse map (that
  measured +90 to +177 MB per process). detect_lang's dictionary vote counts
  such words, so Czech without diacritics is recognised: 45 → 4 of 110 JPZ
  questions undetected. On the JPZ set, exact matches for diacritics-less
  variants 61 % → 96 %; nothing else moved. The search service preloads the
  dictionary at start (0.3 s per worker).
- `qa_lexical` and `qa_vector` give **no curated answer across opposite
  polarity** ("nepřijde" vs "přijde"); `qa_lexical` offers the entry as a
  suggestion instead (`negation_conflict` in
  [`qa_common.py`](../../search/app/nodes/qa_common.py)).
- [Migration 217](../../postgres/migrations/217_synonyms_meeting_groups.sql): ten
  single-word synonym groups (syn/dcera/dítě/žák/uchazeč, stravování, PPP,
  matematika, čeština, učitel, grades 1, 2, 4, 5).

Measured with [`tools/lab/variants`](../../tools/lab/variants/README.md) on the
JPZ set (110 questions, 640 variants): flipped-negation questions answered with
the original curated answer 39/39 → 0/39 (all 39 offered as a suggestion);
synonym variants answered 79 % → 100 %; diacritics-less and typo variants
unchanged.

## Order

1. Build **both** images; one side on 3.0.0 reduces differently.

   ```bash
   docker compose build edu_ai_search edu_ai
   docker compose up -d edu_ai_search edu_ai
   docker exec -i edu_ai_search python -c "import eduai_normalize as e;print(e.__version__)"
   docker exec -i edu_ai /app/.venv/bin/python -c "import eduai_normalize as e;print(e.__version__)"
   ```

   Both must report `3.3.0`.
2. Migration 217. It lives in `postgres/migrations/` and is listed in the
   release manifest [`R217`](../../postgres/releases/R217.json), generated on an
   isolated reference from B216. The runner (`scripts/migrate.py apply`) is
   approved for isolated synthetic databases only
   ([spec](../../specs/active/spec.migration-registry.md)); taking over an
   existing installation (D11) is not decided, so this note does not claim a
   supported upgrade path for one.
3. **Re-ingest every QA pack and every document.** Stored `lemma_text` and
   `stem_text` were built with 3.0.0: a stored "nesmí" still reads `smet` and
   no longer meets a 3.3.0 query "nesmím" (`nesmet`), stored stems still
   carry the leaked stop-words, and words a document typed without
   diacritics keep their old lemma. The norm form is unchanged, so matching
   degrades instead of failing, but the fixes only work after the re-ingest.
4. Parity: `contracts/parity/check_vectors.py` (command in
   [AGENTS.md](../../AGENTS.md)) must pass.

The stored reduced forms of `qa_stopword`, `qa_blocklist` and `qa_synonym` were
recomputed on 21 Oct 2026: no row differs because of these changes (the
guard's phrases are stored with diacritics; meta and identity phrases are
matched folded, not lemmatized). 27
`qa_synonym` rows differ from a recomputation for OLDER reasons (the de/es
interrogative groups, "začít/začínat", "fotit"), the drift migration 211
already names ("sjednotit až s přepočtem"); not touched here.

## Replay on the production log (22 Oct 2026)

A production dump (4 442 logged questions, 373 active QA entries, 1 348
chunks) was replayed with [`tools/lab/replay`](../../tools/lab/replay/README.md):
old code on data ingested by the old code against 3.3.0 + migration 217 on data
re-ingested by 3.3.0. No question got a different curated entry. 42 questions
newly answered from QA (mostly right: questions about the date of the entrance exam,
a test in Czech, the canteen), 23 no longer (9 of them wrong before, e.g. a question
about what not to bring to the exam answered with the list of allowed aids; one
question asked 12× is now only a suggestion: the old answer rested on the leaked
stop-word stem `jso`). 3 questions (8 log rows) newly get a wrong confident answer,
e.g. a short question about phones in school leading to an answer about grades in
the entrance procedure (the restored lemma `škola` plus the verb reach coverage 0.61).

Two decision-logic fixes were measured and **rejected**: breaking a rank tie by
coverage turned 105 more questions into confident answers, many wrong (the
"rank tie → suggestion" rule is a real safeguard); weighting a negated word by
its positive form changed one question, for the worse. The remaining cases are
for the curated data (alternatives, an entry for an ambiguous question), not
for the ranking.

The production also lemmatizes differently from this repository (stored
`nepřítomnost` → `přítomnost`, `mám` → `mama`): it runs an older simplemma.

## Not covered

The standalone word "ne" (an index stop-word), "nikdy", "žádný", "bez";
diacritics-less words whose spellings disagree on the lemma (~25 % of the JPZ
words, "muze", "stejne"), which a frequency from the school's own corpus could
decide later; other languages than Czech. `qa_vector`
and the generated answer were not measured (no OpenAI key on the lab).

## Migration 221 (`qa_lexical` `fetch_k` 50 → 200, 3 Nov 2026)

A setting, not code: `qa_lexical` already reads `fetch_k` (the number of variant rows pulled by `ts_rank_cd`
before the aggregation to entries). With 4–5 variants per entry the default 50 cut variants of the right entry
off, so the union of its lemmas was incomplete and the coverage under-estimated. Release manifest `R221`.

Measured with the regression set (3 buttons, on top of 218–220, the migration itself applied in the rolled-back transaction):
score 1,818.5 → 1,853.0 (interval +26 … +43.5), 72 cases better, 3 worse, **no new confident wrong answer**, no silent
loss of the lead over the second entry; the asker sees the right answer A 83.7 → 85.4 %, B 74.0 → 76.1 %, D 45.4 → 51.1 %,
L 40.0 → 45.9 %. Overriding the parameter for the run instead gives D 52.3 % and L 42.4 %: the two differ only in which
3 questions are offered in 25 cases without a confident answer. The cause was found on 6 Nov: candidates with an
equal rank come back in an order the database chooses (see `rank_ties` below); the regression set now measures with
the ties settled, which gives A 85.6, B 76.5, D 50.0, L 42.4 % for the same state. 400 gives about the same,
100 about two thirds of the gain. Not measured: latency of pulling 200 rows instead of 50, other schools, other languages.

**Undo:** set `fetch_k` of the `qa_lexical` params back to `50`.

## Migration 222 (`qa_lexical` `offer_ngram`, 6–7 Nov 2026) — applied on the lab installation 9 Nov

**What it does.** When `qa_lexical` has no confident answer, the LAST of the offered questions (the
"did you mean" list, or the fallback at a dead end) goes to the curated question whose wording is closest
in character 3–5-grams, if the similarity reaches 0.30. It catches derived and colloquial forms the
lemma misses ("třídnické" → "třídní"). Confident answers, the first two offered questions and the
questions beside an answer do not change. Code: [`qa_ngram.py`](../../search/app/nodes/qa_ngram.py),
parameter in [SETTINGS_REFERENCE](../SETTINGS_REFERENCE.md) §3.3. Release manifest `R222`.

**Before applying:** the search image must contain `search/app/nodes/qa_ngram.py` (rebuild it from this
branch); an older image ignores the parameter (no effect, no error).

**Measured** with the regression set on top of 218–221 (ties settled, the migration applied in the
rolled-back transaction): decisions changed 0, confident wrong 34 → 34; the asker sees the right answer
D 50.0 → 55.7 %, L 42.4 → 51.8 %, the gold set of verified real wordings 60.5 → 69.1 %; an extra offered
question for 4.7 % of the questions outside the content. A replay of 2,446 logged questions: decisions
changed 0. 0.5 ms per query.

**After applying it on the lab installation** (9 Nov; labels of eight cases corrected by the curator,
LEDGER 9 Nov): A 85.6 → 88.6 %, B 76.6 → 79.0 %, D 50.0 → 55.7 %, L 43.5 → 52.9 %, G 61.7 → 70.4 %; confident
wrong 31 → 31. With the packs of a school split between two chats (each searching its own pack) the gain
holds: G 61.7 → 67.9 %, confident wrong unchanged.

**Not measured:** operation WITH a key. There `qa_vector` and the generated answer reuse the offer parked
by `qa_lexical` as related questions, so the n-gram question can appear beside those answers too. Other
schools and languages.

**Undo:** remove `offer_ngram` from the `qa_lexical` params (or set it to `false`).

## `rank_ties` (6 Nov 2026) — a parameter, no migration

Without it, candidates with an equal rank come back in the order the database stores them, so after a
re-upload of the packs a few questions can get a different offer and, rarely, a different confident
answer (in the lab: 4–6 of 3,558 questions). With `rank_ties: true` on the `qa_lexical` step the cut at
`fetch_k` keeps every tied variant and an exact tie is settled by the question text. Measured: the
quality is unchanged (confident right and wrong answers equal), two runs agree completely. The lab always
measures with it; switching it on in operation is a decision of the repository owner (not part of the
recommended configuration, no migration).

## Migration 223 (answer step `skip_without_key`, 8 Nov 2026) — applied on the lab installation 10 Nov

**Why.** Without an OpenAI key the cascade still gathers document passages and tries the
generation, which fails: the chat shows "Dočasný technický problém" (`llm_unavailable`). A replay
of a production log with its documents, without a key, ended that way for 1,073 of 4,442
questions (24 %), always after `qa_lexical` decision C.

**What it does.** With `skip_without_key` on the `answer` step and no usable key (absent or the
installer's `CHANGE_ME…` placeholder) the step does not try the generation and ends like an empty
passage pool: the offer parked by `qa_lexical`, else `no_answer` with the fallback questions. The
streaming path does the same. With a real key nothing changes. Code:
[`answer.py`](../../search/app/nodes/answer.py), [`llm.py`](../../search/app/llm.py) (`chat_configured`),
parameter in [SETTINGS_REFERENCE](../SETTINGS_REFERENCE.md) §3.9. Release manifest `R223`.

**Before applying:** the search image must contain this code (rebuild from this branch); an older
image ignores the parameter.

**Measured** on the production copy with migration 223 and the code of this branch, a sample of 100
logged questions: the 50 that ended in `llm_unavailable` all end in `no_answer` (36 with the same
fallback questions, 14 without any, as before), the other 50 do not change; a question takes about
0.4 s instead of 1.6 s because the failing model call is gone. With a key: unit-tested only.

**After applying it on the lab installation** (10 Nov): a live question without a key returns
`no_answer` ("Na tuto otázku zatím nemám odpověď…"), not `llm_unavailable`.

**Undo:** remove `skip_without_key` from the `answer` params (or set it to `false`).
